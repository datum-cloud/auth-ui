# Internationalization

The app is translated with **Lingui 6**. Strings are marked in source with the Lingui macros, extracted into `.po` catalogs, and compiled to TypeScript modules the app imports at runtime.

## Commands

```bash
bun run i18n:extract    # lingui extract --clean  — scan app/, update the .po catalogs
bun run i18n:compile    # lingui compile --typescript — .po → .ts
```

You rarely run these by hand: `lefthook.yml` runs both on every commit that touches `app/**/*.{ts,tsx}`, then stages `app/modules/i18n/locales/` for you. The catalogs are **generated artifacts** — they are excluded from the ESLint and Prettier pre-commit hooks, and you should not hand-edit the `msgid` side of them.

## Where things live

| Path                                | What it is                                                  |
| ----------------------------------- | ----------------------------------------------------------- |
| `lingui.config.ts`                  | Source locale, the `locales[]` array, and the catalog path  |
| `app/modules/i18n/locales/*.po`     | The catalogs — the translation source of truth              |
| `app/modules/i18n/locales/*.ts`     | Compiled output of `i18n:compile`; imported at runtime      |
| `app/modules/i18n/lingui.ts`        | `SUPPORTED_LOCALES`, `DEFAULT_LOCALE`, and `loadMessages()` |
| `app/modules/i18n/lingui.server.ts` | Server-side per-request i18n setup                          |

Two lists must agree, and they are declared in two different files:

- `lingui.config.ts` → `locales: ['en']` — what the **CLI** extracts and compiles.
- `app/modules/i18n/lingui.ts` → `SUPPORTED_LOCALES = ['en']` — what the **app** will detect and serve.

Adding a locale to one but not the other is the classic mistake: the catalog gets generated but is never selectable, or it is selectable and fails to load.

## Current state: English only

`SUPPORTED_LOCALES` is `['en']` today, and `en` is also the `DEFAULT_LOCALE` and the `sourceLocale`.

There was previously an `es` catalog. It was removed because it was byte-identical to `en` — no real translations — so locale detection could select it and quietly serve English strings labelled as Spanish. Falling back to English explicitly is the honest behavior. If you add a locale, add real translations with it.

## Runtime behavior

`loadMessages(locale)` dynamically imports `./locales/<locale>.po` and returns the raw messages, deliberately **without** activating a global singleton — the messages are handed to a per-request `i18n` instance instead. That keeps SSR safe: concurrent requests in different locales cannot clobber each other's active catalog.
